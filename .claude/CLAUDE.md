# CLAUDE.md - compta

## Project
Household accounting web app: upload French bank CSVs, auto-categorise transactions via substring rules, review them, and explore a monthly dashboard. FastAPI (Python 3.11+, developed on 3.14, CI tests 3.11 and 3.14; stdlib `csv`/`datetime`/`sqlite3`/`tomllib` - no pandas) backend + Next.js 16 / TypeScript / Tailwind frontend.

Detail that only matters when editing specific files lives in path-scoped rules, loaded with those files: `.claude/rules/frontend-pages.md` (every page's UI behaviour, text contrast, Sankey layout, report), `.claude/rules/transfers-triage.md` (pairing and « À classer » algorithms), `.claude/rules/config-files.md` (bank CSV parsing, config/snapshot CSV formats, uploads, the Réglages save). Read the matching one before changing that behaviour from elsewhere.

## Domain Model
- **Transaction** - bank row + `budget_month` (YYYY-MM), `debit_cents`/`credit_cents` (INTEGER cents, never floats), `account` (raw import string, feeds the hash), `account_id` (canonical code), `kind` (`income`/`expense`/`transfer`) + `kind_manual`, `transfer_group_id`, `category_id`, `category_manual`, `note` (free-text, only set on a manual assignment), `rule_id`, `import_hash` (sha256 of account|date|libelle|debit|credit|occurrence - amounts hashed as euro floats for backward compat; the occurrence counter keeps two genuinely identical same-day operations distinct). `import_transactions` also skips a row when its resolved `account_id` already holds as many identical operations as its occurrence, so one statement imported under two aliases of the same account isn't duplicated.
- **Category** - integer `id`, `name`, `parent_id`, `budget_target_cents`; one self-referencing **flow-agnostic** tree (no credit/debit roots - income vs expense lives on the transaction's `kind`). Top-level groups have `parent_id IS NULL`. Names unique per parent; display uses the full path. Renames and re-parenting supported (cycle-checked); no category is undeletable. **Leaf-only assignment**: rules and manual assignments may only target leaves (`api/categories.py::reject_group_target`, 422 on a group). The invariant "a category with children carries no direct rules/transactions" is kept at the edges: **creating** a sub-category under a populated leaf migrates its rules + transactions **down** into the new child (the leaf becomes a group, keeping its budget target; `create_category`); **deleting** a parent's *last* child rolls its rules + manual transactions + target **up** (the parent becomes a leaf again; `delete_category`), while deleting a leaf with siblings drops its rules and target and uncategorises its rows. `reject_populated_parent` blocks re-parenting a node under a populated leaf, and a targeted subtree under a targeted category (`update_category`).
- **Rule** (`label_rules`) - plain substring (NOT regex, case-sensitive `instr`) matched against `Libelle` + `category_id` (leaf only), `priority` (lower wins, ties by id), `is_income_anchor`. Re-applied to all non-manual transactions after every import/rule/category mutation.
- **Account** - `accounts` table (code/label/`type`=`checking`|`savings`/sort_order/`deposit_pattern`); **user data, not code**: loaded from `accounts.csv` via `import_csv.py::import_accounts`; `init_db` seeds none. An account's **names** = code + label + aliases (`account_aliases`, `db.account_names`): import strings resolve on all of them (`load_account_aliases`), transfer labels on all but the code, and a name given to two accounts is rejected. Imports that don't resolve to a known account are rejected. A savings account with a `deposit_pattern` is **external** (no statement, e.g. a child's Livret A, `ENFANT` in the example): its deposits are the checking-account rows whose libellé contains the pattern **case-insensitively** (`str.casefold`, also the SQL function `casefold` registered in `db.connect()`; unlike rules, since banks don't keep a payee's casing). Accounts are not editable in the app: run `reset_db.py` (fresh snapshot), copy that `_backups/<ts>/`, edit its `accounts.csv`, run `reset_db.py --source backup --from <copy>`, and report the edit in `_config/accounts.csv`. The app tracks **flows only, never balances** (owner's decision, 2026-10-26): no opening balance, no running balance, no per-account "how much is left".
- **Transfer** - a debit on one account paired with a same-amount credit on a *different* account within 3 days, where **both** labels start with a transfer marker or name another account (`core/transfers.py::recompute_transfers`). Pairing never guesses: an ambiguous leg stays unpaired for a manual pair (algorithm: `.claude/rules/transfers-triage.md`). Markers: `transfer_markers` table (optional `transfer_markers.csv`, editable in Réglages, `GET|PUT /api/transfer-markers`); empty = `VIR`; case-insensitive **prefix** match, `*` = any label. Both legs get a shared `transfer_group_id` and `kind='transfer'` and are excluded from income/expense totals, the category tree, top merchants and the uncategorised residual; transfers have no category by design (the "sans catégorie" filter skips them). **Manual decisions** (`kind_manual=1`, left alone by `recompute_transfers`): `pair_manually` (`POST /api/transactions/transfer-pair`: one debit + one credit, same amount, two accounts, no window/marker check; releases previous partners so a manual group always has 2 legs) and `set_transfer_mode` (`PUT /api/transactions/{id}/transfer`: `none` = unpair the row + its partner, `transfer` = single-legged, `auto` = back to detection, one row at a time once unpaired). `GET /api/transactions?manual_transfer=true` lists them.

Business rules:
- **Paycheck periods**: `budget_month` boundaries follow income, not the calendar. Credits matching any `is_income_anchor` rule (day ≥ 15 → pays for next month) open a budget month; every transaction from that deposit until the next one belongs to it (`core/periods.py::recompute_budget_months`, re-run after each import and rule mutation). Before the first deposit, or with no anchor rule, calendar months apply.
- **Income/expense** totals come from `transactions.kind` (income = Σ credits of kind income, expenses = Σ debits of kind expense), categorised *and* uncategorised; transfers excluded. The uncategorised credit/debit residual is surfaced as a warning, never an exception.
- **Savings (épargne/désépargne)**: `category_tree` injects derived `synthetic` leaves per `type='savings'` account, named after its label and summed into the tree totals. The net is computed **per budget month** then bucketed by sign: positive months → `epargne` (debit leaf under the `Épargne` top-level group), negative → `desepargne` (credit leaf under `Déficit`); in the all-months view an account can show both, so désépargne never nets away. **Imported** account: net = Σcredit − Σdebit over **all** its rows (any kind); leaf carries `account_id`. **External** account: net = Σdebit − Σcredit of the checking rows matching `deposit_pattern`; leaf carries `libelle_match` (drill-down `GET /api/transactions?deposit_pattern=`, not the case-sensitive `libelle_contains`). Leaves nest under the real `Épargne`/`Déficit` category if present, else a synthetic group. External deposits get `kind='transfer'` from `recompute_transfers` (final pass; single-legged, no `transfer_group_id`, excluded from `transfers_summary`) and are never paired: `_legs` skips them, `pair_manually` rejects them (422), `set_transfer_mode` hands them back to detection whatever the mode (a manual "not a transfer" would count them as an expense *and* as savings). They derive from `deposit_pattern` only, never from categories/rules. Savings interest stays `kind='income'`.
- **Dashboard cards & reconciliation** (`GET /api/dashboard`): **Revenus**, **Dépenses**, **Épargne** (`epargne − desepargne`), **Reste**, so `Revenus − Dépenses − Épargne = Reste`, and `reste = income − expenses − epargne + desepargne` equals the balance-tree total and the Sankey `Reste`/`Découvert` plug. No operating `income − expenses` net (dropped: it clashed with the tree/Sankey totals). `epargne`/`desepargne` come from the tree's `Épargne`/`Déficit` nodes in `api/dashboard.py`. `?month=all` (`ALL_MONTHS`) aggregates every budget month (`month` comes back as `all`). `history` (`monthly_totals`: per-month income/expenses/epargne/desepargne/reste, oldest-first) feeds the deltas and `ResteTrend`. The Sankey (`lib/moneyFlow.ts`) is a frontend-only transform of this payload, gated per leaf, never per group.
- **Budget targets** (`budget_target_cents`, `categorize.py::budget_status`, `PUT /api/categories/{id}/target` `{budget_target: euros > 0 | null}`): a monthly **cap on net spending** on a leaf or a group, **one per branch** (setting one under or above a targeted category is a 422; clearing always works); a group's target covers its subtree, a group without one shows Σ of its children's. Actual = Σdebit − Σcredit of the real flows of the category and everything below it for the month (refunds lower it, transfers excluded); only targeted categories count, so an untargeted income leaf never offsets its group. `budget_status` groups targeted categories under their top-level category (deeper levels flattened into the name, `Sortie / Bar`), overruns first, and reports `untargeted` = Σ `kind='expense'` debits outside any target. "Tous les mois": targets × `budget.months`. `set_category_target` refuses (422) a category whose real flows over the last 12 complete months are net credit, anything in `Déficit`, and anything below `Épargne`; a target on the top-level `Épargne` group itself (`SAVINGS_GROUP`) is the **monthly savings goal** (a floor): returned as `budget.savings_target` and compared with `savings_actual` (= the Épargne card). `income_reference` = the net average month of the top-level `Revenus` group (`INCOME_GROUP`) over the last 12 complete months (so no rent received, refunds or savings withdrawn), for the budget balance; read-only context, the cards are untouched.
- **Monthly averages** (`categorize.py::category_averages`, `GET /api/dashboard/averages?months=3|6|12|all&month=`): the average month per top-level category over the last N **complete** budget months (`averaging_window`: the latest budget month is always excluded, still filling; fewer months than asked → averages what exists). Divisor = budget months in the window (an empty month counts as 0). Spending vs income is decided **per leaf on its net over the whole window** (a one-off refund month never flips a spending leaf): net debit → `expenses` = (Σdebit − Σcredit) / months, net credit → `income`; a leaf with no net takes its side from the displayed month. Groups sum their leaves; `target` = own target, else Σ of the children's. Each leaf's counter-side flows (a refund on Courses, a debit on Loyers) go to `offset`, so rows + `Non classé` (gross) + offset = the card averages exactly (for normal data, where `kind` follows the sign). Savings per account from `_savings_month_nets` (bucketed like `_savings_by_month`) add up to the Épargne card average; `totals` = the mean of the window's `monthly_totals`. `month_*` values are the displayed month's, on the window's side; in « Tous les mois » `month` is null.
- **`PATCH /api/transactions/{id}`** (`TransactionPatch`): updates only the keys sent (`model_fields_set` distinguishes omitted from null). Setting a category → `category_manual=1`, `rule_id=NULL`; `category_id: null` re-runs `apply_rules`. Manual assignments are never clobbered by `apply_rules`; `kind_manual=1` is likewise left alone by `recompute_transfers`. `?manual=true` lists `category_manual=1` rows.
- **Schema**: single version, **no migration ladder** (early dev). `init_db` runs `SCHEMA` (CREATE IF NOT EXISTS) and seeds nothing. If the schema changes, rebuild with `reset_db.py --source live` - don't write migrations yet.

### Rebuild model
- **`reset_db.py` is the one rebuild CLI.** A rebuild = fresh DB + load `accounts.csv` + import every `_inputs/*.csv` (account inferred from the filename via the aliases, deduped by hash) + load a taxonomy (categories, rules, overrides) from `--source {live|defaults|backup}`, then recompute periods + transfers and re-apply rules.
- **Transactions always come from `_inputs/`**, so a snapshot is **config-only**: a full restore point = the latest `_backups/<ts>/` **plus** the current `_inputs/`. Whenever a DB exists, `reset_db.py` snapshots it *before* deleting (and `--source live` rebuilds from that very snapshot).
- **Manual overrides** (`category_manual=1`, `kind_manual=1`, a manual `note`) reference rebuilt ids, so they survive a rebuild only through `overrides.csv` (snapshot or config dir), keyed by the stable `import_hash` with an identity-column fallback. Format and matching: `.claude/rules/config-files.md`.
- `bank_profiles.toml` and `settings.toml` are read from the config dir (`db.DEFAULT_CONFIG_DIR` = `$COMPTA_CONFIG_DIR` else `_config/`) on every call, by the server (`app.state.config_dir`) and `reset_db.py` whatever `--source` - never from a snapshot.

Gotchas:
- Don't change the `_row_hash` formula for occurrence 0 - it must keep matching hashes of rows already in users' databases. The same goes for everything that feeds it: `DEFAULT_PROFILE`, the unstripped `Libelle`, the `,`-decimal amount path of `parsing._parse_number`, and the unstripped `infer_account` string. `TestDefaultFormatFrozen` (test_parsing.py) pins golden hashes. Uploads use the filename-inferred account string, like rebuilds, so their hashes match.
- **Start date** (`settings.toml` `start_date = 2026-03-25`, a TOML date; `core/settings.py::load_start_date`): rows whose **value date** is earlier are dropped before `import_transactions` (`parsing.rows_since`, in `upload_csv` and `import_inputs_dir`; counted in `rows_before_start`), so old history stays in `_inputs/`, out of the DB, and nothing downstream filters by date. Pick the value date of the paycheck opening the first budget month wanted (a later day leaves that month without its income). Moving it takes a `reset_db.py` rebuild; overrides of dropped rows are skipped with a count and stay in the snapshot.
- Env paths: `COMPTA_DB` (default `<repo>/compta.db`; snapshots go to `_backups/` **next to the DB**, `core/config_export.py::backups_dir`, so a demo DB never adds a restore point to the real `<repo>/_backups/`), `COMPTA_INPUTS_DIR` (default `<repo>/_inputs`, `db.DEFAULT_INPUTS_DIR`, `app.state.inputs_dir`), `COMPTA_CONFIG_DIR`. Tests: autouse conftest fixtures point the config dir and inputs dir at `tmp_path`, so the private config never leaks in.
- The demo's `PRLV EDF CLIENTS PARTICULIERS REGUL` is a deliberate near miss of the case-sensitive EDF rule, so « À classer » shows a suggestion.
- Next.js 16: read `frontend/node_modules/next/dist/docs/` before assuming API shapes (see frontend/AGENTS.md).
- The frontend is **desktop-only**: check layouts at ~1400 px; don't file or fix phone-width issues. Existing small-screen code (the Sankey's sideways scroll, wrapping headers) can stay.
- The frontend is light-theme only - `globals.css` pins `color-scheme: light`; don't reintroduce a `prefers-color-scheme` block without styling dark properly.

## Conventions
- Rule patterns are plain substrings - never regex metacharacters.
- `core/` does logic only - no FastAPI imports; routers do I/O orchestration and HTTP errors.
- `db.connect()` is a contextmanager (commit/rollback/close) - check `cur.rowcount` inside the `with` block.
- Amounts: cents (int) in the DB and core logic; convert with `db.euros`/`db.to_cents`. The one exception: `core/categorize.py`'s dashboard aggregates (`category_tree`, `income_and_expenses`, `uncategorized_balance`, `transfers_summary`, `monthly_totals`, `budget_status`) already return euros, and `api/dashboard.py` combines them with `round(..., 2)`.
- Type hints on all public functions; Pydantic models in `schemas.py` for everything crossing the API. `frontend/src/lib/api.ts` mirrors those shapes by hand (no OpenAPI generation: several dashboard payloads are `dict[str, Any]`): change it in the same commit as any response shape.
- Routes: dependencies and `Query`/`Form` params as `Annotated` (`db_path: DbPath`, aliases in `api/deps.py`); the response model comes from the return annotation, no `response_model=` (ruff `FAST` enforces both).
- **Git**: no pull requests in this project - commit directly to `main` and push (a session working on another branch fast-forwards `main` to it once checks pass). No bot PRs either: the owner removed the Dependabot config (2026-09-27); update dependencies by hand (`pip list --outdated`, `npm outdated`), never re-add it.
- **Backlog**: `backlog/{bug,feat,tech}/<slug>.md`, one item per file (template in `backlog/README.md`): context, everything needed to fix or investigate, dated progress notes. Update the item while working on it; delete the file in the commit that finishes it. No ids, no priorities.
- Backend formatted by `ruff format` (110 cols); `ruff check` and the frontend eslint must pass (CI enforces). Never hand-resolve a formatting conflict: re-run `ruff format`.
- **Language**: user-facing frontend strings are French (typographic apostrophe U+2019 in the code, not `'`, to satisfy `react/no-unescaped-entities`); code, comments, and docs (incl. this file) stay English. French category names in `data/` are data, not UI text. **API error messages are French too** (the pages print a `detail` as it is): the routers' `HTTPException` details, the core messages they pass through (`CsvValidationError`, `BankProfileError`, `pair_manually`/`set_transfer_mode` errors - `reset_db.py` prints the same ones), and Pydantic's validation `msg`, rewritten by error `type` (never by its English text) into `<Champ> : <message>` by `api/errors.py::french_validation_errors` (labels in `FIELD_LABELS`; response shape unchanged), and a body that is not valid UTF-8 (FastAPI's English 400, recognised by status + `UnicodeDecodeError` cause, rewritten by `french_http_errors` into the same list shape). Tests assert on these French strings. Pages show `errorMessage(e)`, never `String(e)`. Dates via `frenchMonth`/`frenchDate` (transaction lists show the **value date** `date_valeur`, which orders the list and sets `budget_month`); amounts via `formatEuro` (fr-FR).
- Frontend text colours follow the contrast rules in `.claude/rules/frontend-pages.md` (never `zinc-400`/`zinc-300` for readable text, `green-700`/`red-700` for signed amounts).
