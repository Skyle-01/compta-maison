# CLAUDE.md — compta

## Project
Household accounting web app: upload French bank CSVs, auto-categorise transactions via substring rules, review them, and explore a monthly dashboard. FastAPI (Python 3.11+, developed on 3.14, CI tests 3.11 and 3.14; stdlib `csv`/`datetime`/`sqlite3`/`tomllib` — no pandas) backend + Next.js 16 / TypeScript / Tailwind frontend.

## Domain Model
- **Transaction** — bank row + `budget_month` (YYYY-MM), `debit_cents`/`credit_cents` (INTEGER cents, never floats), `account` (raw import string, feeds the hash), `account_id` (canonical code), `kind` (`income`/`expense`/`transfer`) + `kind_manual`, `transfer_group_id`, `category_id`, `category_manual`, `note` (free-text user annotation, only set on a manual assignment), `rule_id`, `import_hash` (sha256 of account|date|libelle|debit|credit|occurrence — amounts hashed as euro floats for backward compat; occurrence counter keeps two genuinely identical same-day operations distinct); `import_transactions` also skips a row when its resolved `account_id` already holds as many identical operations as its occurrence, so one statement imported under two aliases of the same account isn't duplicated).
- **Category** — integer `id` (PK), `name`, `parent_id`, `budget_target_cents` (optional monthly spending cap, leaves only — see the budget-targets rule); one self-referencing **flow-agnostic** tree (no credit/debit roots — income vs expense lives on the transaction's `kind`). Top-level groups have `parent_id IS NULL` (`fixe`/`variable`/`immobilier`/…); leaves and sub-groups (`bar` under `sortie`) hang beneath. Names are unique per parent; display uses the full path. Renames and re-parenting supported (cycle-checked). No category is undeletable. **Leaf-only assignment**: rules and manual category assignment may only target leaf categories (no children) — enforced by `api/categories.py::reject_group_target` (422 on a group); the frontend `CategoryPicker` hides group nodes (a top-level category without children is a leaf, and selectable). The invariant "a category with children carries no direct rules/transactions" is maintained at the edges: **creating** a sub-category under a *populated leaf* migrates that leaf's rules + transactions + budget target **down** into the new child (the leaf becomes a clean group; `create_category`), and **deleting** a leaf that is its parent's *last child* rolls its rules + manual transactions + budget target **up** to the parent (which becomes a leaf again; `delete_category`) — deleting a leaf that still has siblings instead drops its rules (and target) and uncategorises its rows. `reject_populated_parent` still blocks **re-parenting** an unrelated node under a populated leaf — rules, transactions or a target (`update_category`).
- **Rule** (`label_rules`) — plain substring (NOT regex, case-sensitive `instr`) matched against `Libelle` + `category_id` (leaf only), `priority` (lower wins, ties by id), `is_income_anchor`. Re-applied to all non-manual transactions after every import/rule/category mutation.
- **Account** — canonical `accounts` table (code/label/`type`=`checking`|`savings`/sort_order/`deposit_pattern`); accounts are **user data, not code**: loaded from `accounts.csv` (`_config/`, a snapshot, or the fictional `data/` example with `PERSO`/`JOINT`/`LIVRET`/`LOCATIF`/`ENFANT`) via `import_csv.py::import_accounts` → `db.upsert_accounts`; `init_db` seeds none. `account_aliases` maps raw import strings (filename-inferred or manual) to a code. Imports are rejected if they don't resolve to a known account. `type='savings'` drives the épargne/désépargne derivation (see business rules). A savings account with a non-null `deposit_pattern` is **external** (no imported statement, e.g. a child's Livret A — `ENFANT` in the example): its deposits are the checking-account rows whose libellé contains that substring, rather than rows of its own.
- **Transfer** — an internal movement: a debit on one account paired with a same-amount credit on a *different* account within 3 days, where **both** labels start with a transfer marker (`core/transfers.py::recompute_transfers` → `pair_legs`: greedy, each leg used once, matched on `date_operation`, credits bucketed by amount and bisected by day). Markers: `transfer_markers` table (loaded from optional `transfer_markers.csv`, editable in Settings / `GET|PUT /api/transfer-markers`); empty table = built-in `DEFAULT_TRANSFER_MARKERS` (`VIR`); case-insensitive **prefix** match on the stripped label (unlike rules, which are substrings anywhere); `*` = any label (legacy amount+date pairing). Both legs get a shared `transfer_group_id` and `kind='transfer'` and are excluded from income/expense totals, the category tree, top merchants, and the uncategorised residual. Transfers have no spending category by design: the transactions list shows a "⇄ virement" tag instead of a category picker and the "sans catégorie" filter skips them (`kind != 'transfer'`). **Manual decisions** (`kind_manual=1`, left alone by `recompute_transfers`): `pair_manually` (`POST /api/transactions/transfer-pair`, one debit + one credit, same amount, two accounts, no window/marker check; releases previous partners so a manual group always has 2 legs) and `set_transfer_mode` (`PUT /api/transactions/{id}/transfer`: `none` = unpair the row + its partner, `transfer` = single-legged transfer, `auto` = back to detection, one row at a time once unpaired). The Transactions page ticks up to 2 rows for "Associer en virement" / "Marquer comme virement" and shows Dissocier / Auto on transfer rows. Settings → "Virements manuels" lists every manual decision (`GET /api/transactions?manual_transfer=true` = `kind_manual=1` rows; `lib/manualTransfers.ts::groupManualTransfers` rebuilds pairs from `transfer_group_id`) with an Auto action.

Business rules:
- **Paycheck periods**: `budget_month` boundaries follow income, not the calendar. Credits matching any `is_income_anchor` rule (day ≥ 15 → pays for next month) open a budget month; every transaction from that deposit until the next one belongs to it (`core/periods.py::recompute_budget_months`, re-run after each import and rule mutation). Before the first deposit, or with no anchor rule at all, calendar months apply.
- **Income/expense** totals come from `transactions.kind` (income = Σ credits of kind income, expenses = Σ debits of kind expense), spanning categorised *and* uncategorised rows; transfers excluded. The leftover uncategorised credit/debit residual (transfers removed) is surfaced as a warning, never an exception.
- **Savings (épargne/désépargne)**: `core/categorize.py::category_tree` injects derived leaves per `type='savings'` account from `_savings_net_cents`. The net is computed **per budget-month** then bucketed by sign: `epargne_cents` = Σ of positive months (money saved → outflow/debit leaf under the `Épargne` top-level group), `desepargne_cents` = Σ|net| of negative months (money dipped into → inflow/credit leaf under `Déficit`). Both leaves are named after the account label. For a single `month` only one side is non-zero; in the **all-months view an account can show both** (saved some months, withdrew others) — that's how désépargne stays visible instead of netting away. **Imported** account (no `deposit_pattern`, e.g. LIVRET): per-month net = Σcredit − Σdebit over **all** its own rows (any kind — a paired transfer leg, interest, …); the leaf carries `account_id` for drill-down. **External** account (`deposit_pattern` set, the kids' Livret A): per-month net = Σdebit − Σcredit of the checking-account rows matching the pattern (a debit out = a deposit in); the leaf carries `libelle_match` (the pattern) for drill-down since the rows live on the funding account. Leaves are `synthetic` and **are** summed into the tree totals. The leaves nest under the real `Épargne`/`Déficit` top-level category if present, else a synthetic group. External-savings deposits are marked `kind='transfer'` by `recompute_transfers` (final pass) so they drop out of expenses like LIVRET legs (single-legged, no `transfer_group_id`; excluded from `transfers_summary`) They are never paired: `_legs` skips them, `pair_manually` rejects them (422), and `set_transfer_mode` hands them back to detection whatever the mode, since a manual "not a transfer" would count them as an expense *and* as savings. External-savings flows are derived from the account's `deposit_pattern`, never from manual categories/rules. Savings-account interest stays `kind='income'`.
- **Balance tree drill-down**: only **leaf** nodes (no children) expand to list their transactions — real category leaves by `category_id`, the uncategorised bucket by the uncategorised filter, derived savings leaves by `account_id`. Group nodes and the root just aggregate children inline (`frontend/src/app/page.tsx::TreeNode`).
- **Money flow Sankey** (`frontend/src/lib/moneyFlow.ts::moneyFlow` + `frontend/src/app/page.tsx::FlowNode`, recharts `<Sankey>`): a **frontend-only** transform of the `Dashboard` payload (no backend change). Income source leaves → `Revenus` hub → central `Budget` → expense groups → leaves, plus an `Épargne` branch and a sign-aware balancing branch (`Reste` surplus right / `Découvert` deficit left). Because income is mixed *into* expense groups (e.g. Salaire under Fixe), values are gated **per leaf** and rolled up — an income source is a leaf with net credit, an expense a leaf with net debit; never the group net (avoids hiding expenses and a Budget↔group cycle). `uncategorised` is shown **gross on both sides** (rendered `Non classé`), so the income total matches `data.income`. The `Reste`/`Découvert` plug = `income − expenses − épargne`, equal to the Balance-tree **total** and the **Reste** card (see dashboard-cards rule). Tiny expense leaves are folded into a per-group `Autres (<group>)` node (< 2.5% of total expenses) so the right edge stays legible.
- **Dashboard cards & reconciliation** (`GET /api/dashboard`): four cards — **Revenus** (income), **Dépenses** (expenses), **Épargne** (net set aside = `epargne − desepargne`), **Reste** — laid out so `Revenus − Dépenses − Épargne = Reste`, and `reste = income − expenses − epargne + desepargne` equals the balance-tree total and the Sankey `Reste`. There is no operating `income − expenses` net (the old Net card and its payload field were dropped: it clashed visually with the Sankey/tree totals). `epargne`/`desepargne` are derived from the tree's `Épargne`/`Déficit` top-level nodes in `api/dashboard.py`. `?month=all` (`api/dashboard.py::ALL_MONTHS`, the dashboard's "Tous les mois" option) aggregates every budget month: `month` comes back as `all`, the hero says "sur l’ensemble de la période", deltas are hidden and drill-downs drop the month filter. The payload also carries a `history` series (`categorize.py::monthly_totals`: per-month income/expenses/epargne/desepargne/reste, oldest-first) powering the per-card month-over-month deltas and the `Reste` sparkline.
- **Budget targets** (`categories.budget_target_cents`, `core/categorize.py::budget_status`, dashboard `budget` payload + `page.tsx::BudgetSection`, colour bands in `lib/budget.ts`): a monthly **cap on net spending** set on a **leaf** only (`PUT /api/categories/{id}/target` `{budget_target: euros > 0 | null}`, 422 on a group); a group shows the sum of its leaves' targets. Actual = Σdebit − Σcredit of the leaf's real flows for the budget month (a refund lowers it; transfers excluded). Only targeted leaves count, so an untargeted income leaf (Salaire under Fixe) never offsets its group. `budget_status` groups targeted leaves under their top-level category (deeper levels flattened into the leaf name, e.g. `Sortie / Bar`; a top-level leaf is a group without leaves), orders groups and leaves by actual/target (overruns first; empty 0/target leaves kept), and reports `untargeted` = Σ `kind='expense'` debits outside any targeted category (uncategorised included). "Tous les mois": targets × the number of budget months (`budget.months`). Savings accounts have no targets (out of scope). The dashboard flows the group cards in CSS columns (no grid-row stretch) and shows a single-leaf group as one `Group · Leaf` line. Read-only context: the cards' reconciliation is untouched. Settings edits targets inline in the Catégories tree (leaf: "＋ objectif" / "300 € / mois" button; group: grey Σ).
- **Categorising a transaction** (Transactions page, `frontend/src/app/transactions/page.tsx`): one inline editor per row (button-confirmed, never instant-on-select). Pick a leaf category, then choose **either** "Cette opération" (a one-off manual assignment) **or** "Règle (opérations similaires)" (creates a `label_rules` rule, with a live debounced match-count preview that reuses `?libelle_contains=&uncategorized=true`). A **description** maps to the transaction `note` in manual mode and to the rule's `description` in rule mode. Manual → `PATCH /api/transactions/{id}` `{category_id, note}`; rule → `POST /api/rules`. Available whether or not the "Sans catégorie uniquement" filter is on. (There is no longer a dashboard suggestions panel; `suggestPattern` in `lib/api.ts` still prefills the rule pattern by stripping a dated prefix.)
- **`PATCH /api/transactions/{id}`** (`TransactionPatch`): updates only the keys the caller actually sent (`model_fields_set` distinguishes omitted from null), so it can set the category, the note, or both. Setting a category → `category_manual=1`, `rule_id=NULL`; clearing it (`category_id: null`) re-runs `apply_rules`. "Delete a manual assignment" (Settings) sends `{category_id: null, note: null}`. `GET /api/transactions?manual=true` lists `category_manual=1` rows (powers the Settings "Modifications manuelles" table).
- Manual category assignments (`category_manual=1`) are never clobbered by `apply_rules`; clearing one re-runs the rules. `kind_manual=1` is likewise left alone by `recompute_transfers`.
- **Schema**: single version, **no migration ladder** (early dev). `init_db` just runs `SCHEMA` (CREATE IF NOT EXISTS) and seeds nothing. If the schema shape changes, rebuild with `reset_db.py --source live` (it snapshots cats/rules/overrides first, then deletes + recreates the DB) — don't write migrations yet.

Gotchas:
- Bank CSVs: the built-in `DEFAULT_PROFILE` is semicolon-delimited, comma-decimal, dd/mm/yyyy, quoted fields; UTF-8 or Windows-1252; amounts may carry space/NBSP thousands separators and a sign (dropped — the Debit/Credit column gives the direction). Other layouts come from `bank_profiles.toml` in the config dir (`db.DEFAULT_CONFIG_DIR` = `$COMPTA_CONFIG_DIR` else `_config/`; example in `data/`), read on every call by **both** the server (`app.state.config_dir`) and `reset_db.py` whatever `--source` — never from a snapshot. `detect_profile` tries user profiles in file order, then the default; the first whose columns all sit on one of the first 30 lines wins, and a row error never falls through to the next profile. A missing value-date column falls back to the operation date; a signed `amount` column splits into Debit (negative) / Credit, never `-0.0`. Tests: an autouse conftest fixture points `app.main.DEFAULT_CONFIG_DIR` at `tmp_path/_config` so the private config never leaks in.
- **Taxonomy CSV format** (one shape for the default `data/*.csv`, the Settings "Export CSV" buttons / `GET /api/{categories,rules}/export`, and the `_backups/<ts>/` snapshots): `categories.csv` = `path;budget_target` — full ` / `-joined category paths (the importer get-or-creates each node along the path; assumes names contain no literal ` / `) + the optional monthly target in euros (`450.00`, empty = none; the loader also takes `,` decimals and spaces, rejects ≤ 0 with the line number, drops a target on a node that has children, and reads the column with `row.get` so older `path`-only files and snapshots load); `rules.csv` = `category_path;pattern;priority;is_income_anchor;description`. `is_income_anchor` and `priority` are stored explicitly (no longer derived). `api/categories.py::csv_text` (written by `csv_response` and `reset_db.py`), `category_paths`, `category_rows` (+ `CATEGORIES_HEADER`; reads targets only if the column exists, so `--source live` can snapshot a DB built before it), `api/rules.py::rule_rows` and `api/transactions.py::override_rows` build both the Settings exports and the snapshots; `import_csv.py` (`import_categories`/`import_rules`) loads them and is shared by `reset_db.py`.
- **`reset_db.py` is the one rebuild CLI.** A rebuild = fresh DB + load `accounts.csv` + import every `_inputs/*.csv` (account inferred from filename via the aliases, deduped by hash) + load a taxonomy (cats/rules/+overrides) from `--source {live|defaults|backup}`, then recompute periods+transfers and re-apply rules. **Transactions always come from `_inputs/`**, so a snapshot is **config-only** (accounts + taxonomy + overrides; a pre-accounts.csv snapshot borrows `accounts.csv` from the config dir): a full restore point = the latest `_backups/<ts>/` **plus** the current `_inputs/`. Whenever a DB exists, `reset_db.py` snapshots it to `_backups/<ts>/` *before* deleting — so every rebuild leaves a recoverable restore point (and `--source live` rebuilds from that very snapshot). `import_csv.py` is the shared loader (no longer a CLI of its own).
- **`accounts.csv` format**: `code;label;type;sort_order;deposit_pattern;aliases` (unknown columns, e.g. the removed `include_in_full_view`, are ignored) — `type` = `checking`|`savings`; `deposit_pattern` only for external savings; `aliases` = `|`-separated import strings (the code is always one). An alias must match the account part `infer_account` pulls from the statement filename (`RELEVE_[COMPTE_]<ACCOUNT>_<yyyy>…`, or a bank profile's `filename_pattern` `account` group; underscores → spaces), exactly or as a contained substring. Snapshots (`_backups/<ts>/accounts.csv`) use the same format.
- **Manual overrides** (`category_manual=1` / `kind_manual=1` / a manual `note`) don't survive a rebuild on their own — they reference rebuilt category ids. They're captured in the `_backups/<ts>/overrides.csv` snapshot (and Settings → "Modifications manuelles" / `GET /api/transactions/export-overrides`): CSV `import_hash;category_path;kind;libelle;note;transfer_pair;account_id;date_operation;debit_cents;credit_cents`, keyed by the **stable `import_hash`**, not row id. `resolve_overrides` matches each row by `import_hash`, falling back to its identity columns (account, date, libellé, amounts; identical operations matched in order, never twice) when the hash isn't in the DB — rows uploaded before the upload/rebuild hash fix were hashed with the account code, not the filename alias. `import_overrides` applies them and runs *before* the recompute tail (apply_rules skips `category_manual=1`, recompute_transfers leaves `kind_manual=1` legs alone); the `note`, `transfer_pair` and identity columns are read with `row.get` so older exports without them still load (hash-only). `transfer_pair` = the partner leg's `import_hash` for a manual pair (self-join in `api/transactions.py::override_rows`, shared by the API export and `reset_db.py`); `import_overrides` clears any auto group on a manual-kind row and `restore_manual_pairs` re-links pairs before the recompute tail. Rows found neither way (statement not re-imported) are skipped with a count.
- Next.js 16: read `frontend/node_modules/next/dist/docs/` before assuming API shapes (see frontend/AGENTS.md).
- The frontend is light-theme only — `globals.css` pins `color-scheme: light`; don't reintroduce a `prefers-color-scheme` block without styling dark properly.
- The DB path is `COMPTA_DB` env var, default `<repo>/compta.db`; the statement archive is `COMPTA_INPUTS_DIR`, default `<repo>/_inputs` (`db.DEFAULT_INPUTS_DIR`, `app.state.inputs_dir`; conftest points it at `tmp_path/_inputs`).
- **Uploads match rebuilds** (`api/imports.py::upload_csv`, `core/inputs.py`): the account string feeds `import_hash`, so when the picked account (the Import page sends the code) resolves to the same code as the filename-inferred string, the upload uses the inferred string, exactly like `reset_db.py`. Each upload is copied to `_inputs/` (`archive_statement`): under its own name when that infers the account, else `RELEVE_<account>_<today>_<name>.csv`; a clash with a different file gets ` (2)`…, identical bytes are reused; `ImportResult.archived_as` is `None` when no name would re-infer the account.
- Don't change the `_row_hash` formula for occurrence 0 — it must keep matching hashes of rows already in users' databases. The same goes for everything that feeds it: `DEFAULT_PROFILE`, the unstripped `Libelle`, the `,`-decimal amount path of `parsing._parse_number`, and the unstripped `infer_account` string. `TestDefaultFormatFrozen` (test_parsing.py) pins golden hashes.

## Conventions
- Rule patterns are plain substrings — never regex metacharacters.
- `core/` does logic only — no FastAPI imports; routers do I/O orchestration and HTTP errors.
- `db.connect()` is a contextmanager (commit/rollback/close) — check `cur.rowcount` inside the `with` block.
- Amounts: cents (int) in the DB and core logic; convert with `db.euros`/`db.to_cents`. The one exception: `core/categorize.py`'s dashboard aggregates (`category_tree`, `income_and_expenses`, `uncategorized_balance`, `transfers_summary`, `monthly_totals`, `budget_status`) already return euros, and `api/dashboard.py` combines them with `round(..., 2)`.
- Type hints on all public functions; Pydantic models in `schemas.py` for everything crossing the API. `frontend/src/lib/api.ts` mirrors those shapes by hand (no OpenAPI generation: several dashboard payloads are `dict[str, Any]`): change it in the same commit as any response shape.
- Routes: dependencies and `Query`/`Form` params as `Annotated` (`db_path: DbPath`, aliases in `api/deps.py`); the response model comes from the return annotation, no `response_model=` (ruff `FAST` enforces both).
- **Git**: no pull requests in this project — commit directly to `main` and push (a session working on another branch fast-forwards `main` to it once checks pass).
- **Backlog**: `backlog/{bug,feat,tech}/<slug>.md`, one item per file (template in `backlog/README.md`): context, everything needed to fix or investigate, dated progress notes. Update the item while working on it; delete the file in the commit that finishes it. No ids, no priorities.
- Backend formatted by `ruff format` (110 cols); `ruff check` and the frontend eslint must pass (CI enforces). Never hand-resolve a formatting conflict: re-run `ruff format`.
- **Language**: user-facing frontend strings are French (typographic apostrophe `’`, not `'`, to satisfy `react/no-unescaped-entities`); code, comments, and docs (incl. this file) stay English. French category names in `data/` are data, not UI text. Date display uses `frenchMonth` / `frenchDate` (`Intl`, fr-FR; transaction lists show the **value date** `date_valeur`, the one that orders the list and sets `budget_month`); amounts use `formatEuro` (fr-FR).
